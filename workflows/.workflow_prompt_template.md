# Workflow 生成 Prompt 模板

## 第一步：匹配 Pattern（必须）

先判断任务属于下面哪个 pattern，**直接按该 pattern 的结构生成**，不做自由发挥。

### 快速匹配表

| 任务特征 | 匹配 Pattern |
|---------|------------|
| 游戏开发（植物大战僵尸、贪吃蛇等） | **⑩ 游戏开发专用** |
| 代码生成（写完整项目/多模块） | **③ 复杂 DAG** |
| 多源搜索/多平台对比 | **① 纯并行 → 汇总** |
| 分析→报告（先搜后写） | **② 串行流水线** |
| 遍历文件批量处理 | **④ 动态批量** |
| 项目分析（分析项目结构/技术栈） | **⑤ CodeGraph预扫描→多Agent分析** |
| 迭代优化/Loop | **⑥ 迭代循环** |
| 方案审查/安全审核 | **⑦ 产出→验证** |
| 方案选优/技术选型 | **⑧ 多方案 Tournament** |
| 多源搜索（容错） | **⑨ 容错并行** |
| 多阶段任务 | 可返回多个编号，如 "⑤+②" |

**匹配不到才自由生成，且必须用 parallel() 或 $dag 实现并发，禁止纯串行。**

## 第二步：选 API（按匹配表中的 pattern 对应的示例代码选）

## 固定结构

```js
export const meta = {
  name: "简短名称",
  description: "一句话描述",
  phases: [
    { title: "阶段1", detail: "说明" },
    { title: "阶段2", detail: "说明" },
  ],
}

export default async function () {
  // ...
}
```

## API 使用规则

### agent(prompt, opts)
- 必须始终传 `label` — 用于进度显示和日志
- 最终结果输出的 agent 传 `isFinal: true`

### parallel([thunks])
- ⚠️ **优先考虑它，能 parallel 就别串行**
- 参数必须是函数数组：`[() => agent(...), () => agent(...)]`

### $dag({key: spec})
- 只在**有依赖关系**时才用
- 步骤可以函数（无依赖）或 `{depends, task}` 对象

### phase(title)
- 每个 phase 必须对应 meta.phases 中的一项

### 其他
- `log(msg)` — 输出进度消息
- `budget.remaining()` — 查看 token 余量
- `workflow(nameOrRef, args)` — 调用子 workflow

## 并发强制规则（必须遵守）

1. 匹配到 pattern 后，**严格按该 pattern 的结构生成**，不要自己改
2. 独立模块**必须并行**，禁止写成 `await agent()` 串联
3. 代码生成类任务：设计 agent 只写 DESIGN.md，实现 agent 各写各的文件，集成 agent 用 read_file 合并
4. 所有 agent 调用必须 await

## 流程图层次规则（必须遵守）

1. **阶段必须分层**：每个 `phase()` 是一个独立层次，用 `meta.phases` 按顺序声明
2. **数据流即边**：串行阶段之间必须显式传递数据（前一个 agent 的输出拼接进后一个 agent 的 prompt），`$dag()` 会自动生成依赖边
3. **并行阶段用 fan-out/fan-in**：
   - 扫描阶段(1个 agent) → 并行分析阶段(N个 agent)：扫描结果传给每个分析 agent → **生成 fan-out 边**
   - 并行分析阶段(N个 agent) → 报告阶段(1个 agent)：所有分析结果传给报告 agent → **生成 fan-in 边**
4. **禁止孤立节点**：每个 phase 内的 agent 必须有入边或出边，不能悬挂
5. **agent label 必须体现层级**：label 格式 `"阶段名：具体任务"`（如 `"扫描：CodeGraph"`），便于流程图展示

## 10 种编排模式（完整示例）

---

### ① 纯并行收集 → 汇总（最常用）

```
适用：多源搜索、多维度分析、批量调研
选择理由：多个子任务彼此完全独立，最后只需一次汇总
```

```js
export const meta = {
  name: "多源对比分析",
  description: "并行搜索三个平台数据，综合对比分析",
  phases: [
    { title: "并行搜索", detail: "同时搜索多个数据源" },
    { title: "综合分析", detail: "汇总对比" },
  ],
}

export default async function () {
  phase("并行搜索")

  // ✅ 正确：parallel 里是 thunk（函数），不是直接传 Promise
  const [baidu, weibo, zhihu] = await parallel([
    () => agent("搜索百度热搜", { label: "百度" }),
    () => agent("搜索微博热搜", { label: "微博" }),
    () => agent("搜索知乎热榜", { label: "知乎" }),
  ])

  phase("综合分析")
  return await agent(
    `对比分析以下三个平台的热点异同：\n百度：${baidu}\n微博：${weibo}\n知乎：${zhihu}`,
    { label: "综合对比", isFinal: true }
  )
}
```

### ② 串行流水线（前一步输出传给后一步）

```
适用：搜索→分析→报告、读取→处理→输出
选择理由：每一步的数据依赖上一步的输出
```

```js
export const meta = {
  name: "调研分析报告",
  description: "先搜索数据，再分析，最后写报告",
  phases: [
    { title: "搜索", detail: "搜索原始数据" },
    { title: "分析", detail: "深度分析" },
    { title: "报告", detail: "生成最终报告" },
  ],
}

export default async function () {
  phase("搜索")
  const raw = await agent("搜索 2026 年 AI Agent 的最新发展", { label: "搜索数据" })

  phase("分析")
  const analysis = await agent(`分析以下数据的关键趋势：\n${raw}`, { label: "深度分析" })

  phase("报告")
  return await agent(`根据分析结果写报告：\n${analysis}`, { label: "生成报告", isFinal: true })
}
```

### ③ 复杂 DAG 拓扑（部分依赖 + 部分并行）

```
适用：代码生成（设计→并行写模块→合并）、有分支依赖的多步流程
选择理由：有些步骤必须等前序完成，有些可以并行跑
⚠️ 只有这种场景才用 $dag，不要什么任务都套 $dag
```

```js
export const meta = {
  name: "模块化开发",
  description: "先设计架构，再并行实现各模块，最后集成",
  phases: [
    { title: "设计", detail: "架构设计" },
    { title: "实现", detail: "并行实现各模块" },
    { title: "集成", detail: "合并代码" },
  ],
}

export default async function () {
  const ctx = await $dag({
    // ⚠️ 设计 agent 只能用 write_file 写 design.md，不要写代码
    架构设计: () => agent(
      "设计项目架构，用 write_file 将设计文档写入 DESIGN.md（只写设计，不要写任何代码）",
      { label: "架构设计" }
    ),

    // 每个实现 agent 写自己独立的文件
    引擎模块: {
      depends: "架构设计",
      task: (ctx) => agent(
        `用 write_file 实现游戏引擎模块，写入 src/engine.js\n参考设计：${ctx["架构设计"]}`,
        { label: "引擎" }
      ),
    },
    UI模块: {
      depends: "架构设计",
      task: (ctx) => agent(
        `用 write_file 实现 UI 模块，写入 src/ui.js\n参考设计：${ctx["架构设计"]}`,
        { label: "UI" }
      ),
    },

    // 集成 agent 用 read_file 读各模块文件，合并写入最终文件
    集成: {
      depends: ["引擎模块", "UI模块"],
      task: (ctx) => agent(
        `用 read_file 读取 src/engine.js 和 src/ui.js，合并写入最终文件 index.html`,
        { label: "集成", isFinal: true }
      ),
    },
  })

  return ctx["集成"]
}
```

**代码生成关键规则**：
- 设计 agent **只能写设计文档**（.md），不要写任何代码
- 每个实现 agent 只写自己的文件，不要读/写其他模块的文件
- 集成 agent 用 `read_file` 读各模块文件，再合并

### ④ 动态批量处理（先发现列表，再并行处理每个）

```
适用：遍历文件→每个文件开 agent、遍历结果集→每个单独分析
选择理由：执行前不知道有多少项需要处理
```

```js
export const meta = {
  name: "批量代码审查",
  description: "扫描所有 py 文件并逐个审查",
  phases: [
    { title: "扫描", detail: "获取文件列表" },
    { title: "审查", detail: "并行审查每个文件" },
    { title: "汇总", detail: "汇总结果" },
  ],
}

export default async function () {
  phase("扫描")
  // 第一步：获取要处理的列表
  const fileList = await agent("列出当前目录下所有 .py 文件，只返回文件名，每行一个", { label: "文件列表" })
  const files = fileList.trim().split("\n").filter(Boolean)

  phase("审查")
  // 第二步：对每个文件开一个 agent 并行处理
  const reviews = await parallel(
    files.map((f) => () => agent(`审查文件 ${f} 的代码质量`, { label: `审查:${f}` }))
  )

  phase("汇总")
  return await agent(`汇总以下审查结果，列出问题最多的前三个文件：\n${reviews.join("\n\n")}`, { label: "汇总报告", isFinal: true })
}
```

### ⑤ CodeGraph 预扫描 → 多Agent深度分析（项目分析专用）

```
适用：分析任何项目的结构、技术栈、核心功能
选择理由：先用 CodeGraph 扫描完整项目结构（零 LLM 调用），再把结构数据传给多个 Agent 并行分析不同维度（入口/组件/公共模块），最后综合生成 HTML 报告
关键规则：
  1. 第1个 Agent 强制只用 codegraph_files/codegraph_explore，禁止 read_file
  2. 中间分析 Agent 不许自己重新扫描或写文件，只分析收到的 structure 文本
  3. 中间 Agent 只输出分析文本，不要写任何文件
  4. 最终报告强制用绝对路径写到桌面 ~/Desktop/
```

```js
export const meta = {
  name: "项目深度分析",
  description: "CodeGraph 扫描 → 并行多维度分析 → 生成 HTML 报告",
  phases: [
    { title: "扫描", detail: "CodeGraph 扫描项目结构" },
    { title: "并行分析", detail: "多 Agent 并行分析架构/组件/公共模块" },
    { title: "报告", detail: "综合生成 HTML 报告" },
  ],
}

export default async function () {
  phase("扫描")
  // 第一步：用一个 Agent 扫项目结构（用 codegraph_files / codegraph_explore）
  const project_path = args && args.path ? args.path : "."
  const structure = await agent(
    `【强制规则 - 必须遵守】
1. ⚠️ 只用 codegraph_files 和 codegraph_explore 工具，严禁使用 read_file
2. 先调用 codegraph_files 获取完整目录树
3. 再调用 codegraph_explore 分析入口、路由、配置、工具函数
4. 扫描完成后直接输出文本描述，不要 write_file 写任何文件
5. 必须 3 轮内完成，超时直接输出已有数据

扫描项目：${project_path}
输出格式：文件树概述 + 技术栈 + 入口文件 + 包配置`,
    { label: "CodeGraph 扫描", timeout: 120, agentType: "Explore" }
  )

  phase("并行分析")
  // 第二步：把扫描结果传给多个 Agent 并行分析不同维度
  log("正在并行分析项目各维度...")
  const [arch, modules, tech] = await parallel([
    () => agent(
      `【强制规则 - 必须遵守】
1. ⚠️ 只分析下面提供的项目结构数据，不要自己重新扫描或读文件
2. ⚠️ 禁止使用 write_file，只输出分析文本
3. 直接给出分析结论，不要绕圈子

基于以下项目结构数据，分析项目架构设计：
- 入口与路由、模块依赖关系
- 框架选型和架构模式
- 数据流和通信机制

项目结构：${structure.slice(0, 5000)}`,
      { label: "架构分析" }
    ),
    () => agent(
      `【强制规则 - 必须遵守】
1. ⚠️ 只分析下面提供的项目结构数据，不要自己重新扫描或读文件
2. ⚠️ 禁止使用 write_file，只输出分析文本
3. 直接给出分析结论，不要绕圈子

基于以下项目结构数据，分析项目的核心模块和组件：
- 主要业务模块的功能职责
- 组件复用和层级关系
- 公共模块（工具函数/hooks/服务层）

项目结构：${structure.slice(0, 5000)}`,
      { label: "组件分析" }
    ),
    () => agent(
      `【强制规则 - 必须遵守】
1. ⚠️ 只分析下面提供的项目结构数据，不要自己重新扫描或读文件
2. ⚠️ 禁止使用 write_file，只输出分析文本
3. 直接给出分析结论，不要绕圈子

基于以下项目结构数据，分析项目的技术栈：
- 编程语言、框架、构建工具
- 主要依赖库及其用途
- 代码质量和工程实践

项目结构：${structure.slice(0, 5000)}`,
      { label: "技术栈分析" }
    ),
  ])

  phase("报告")
  // 第三步：综合生成 HTML 报告
  log("正在生成 HTML 分析报告...")
  const project_name = project_path === "." ? "project" : project_path.split("/").filter(Boolean).pop()
  const report_path = `~/Desktop/${project_name}-analysis.html`
  const report = await agent(
    `基于以下三个维度的分析结果，用 write_file 生成一份完整的 HTML 分析报告，写入 ${report_path}。
【注意】路径是 ~/Desktop/ 开头，是用户桌面的绝对路径，不要改成其他目录。

报告需要有专业的CSS样式（深色或浅色主题皆可），结构清晰。

架构分析：
${arch}

模块分析：
${modules}

技术栈分析：
${tech}

请直接写 HTML 文件，包含完整页面结构和样式。`,
    { label: "生成报告", isFinal: true }
  )
  return report
}
```

### ⑥ 迭代循环（检查评分）

```
适用：代码优化、Bug修复、迭代改进
选择理由：一次做不好，需要反复检查直到条件满足
```

```js
export const meta = {
  name: "代码迭代优化",
  description: "不断优化代码质量直到评分达标",
  phases: [
    { title: "优化", detail: "分析和改进代码" },
    { title: "检查", detail: "验证是否达标" },
  ],
}

export default async function () {
  phase("优化")
  let code = await agent("分析 cli/handlers/chat_handler.py 的代码质量问题", { label: "初始分析" })
  let score = 0
  let rounds = 0
  const MAX_ROUNDS = 5

  while (score < 80 && rounds < MAX_ROUNDS) {
    rounds++
    code = await agent(`改进以下代码，使其质量达到 80 分以上：\n${code}`, { label: `改进第${rounds}轮` })
    score = rounds * 20 // 简化示意，实际由 LLM 判断
  }

  phase("检查")
  return await agent(`以下是优化后的最终代码，请做最终审查：\n${code}`, { label: "最终审查", isFinal: true })
}
```

### ⑦ 产出 → 验证（Adversarial Verification）

```
适用：方案审核、安全审查、代码审查、事实核查
选择理由：先出成果，再换一个**独立视角/角色**来审查它，审查发现问题就修订，没问题就通过
关键区别 vs 串行流水线：验证步骤的角色和视角必须和产出步骤不同（比如一个人写、另一个人审）
```

```js
export const meta = {
  name: "方案审查",
  description: "先生成方案，再独立审查其安全性",
  phases: [
    { title: "产出", detail: "生成方案" },
    { title: "验证", detail: "独立审查" },
  ],
}

export default async function () {
  phase("产出")
  const plan = await agent("设计一个用户登录模块的架构方案", { label: "方案设计" })

  phase("验证")
  // ⚠️ 关键：agentType: "Explore" 让验证 Agent 用不同角色/视角审查
  const review = await agent(`从安全角度审查以下方案，指出所有漏洞：\n${plan}`, {
    label: "安全审查",
    agentType: "Explore",
  })

  // 审查发现问题时，让原 Agent 修改
  if (review.includes("漏洞") || review.includes("风险") || review.includes("问题")) {
    const revised = await agent(`根据以下安全审查意见修改方案：\n原方案：${plan}\n审查意见：${review}`, {
      label: "修订方案",
      isFinal: true,
    })
    return revised
  }
  return plan
}
```

### ⑧ 多方案 Tournament（生成 → 对比 → 选优）

```
适用：方案选优、技术选型、架构决策
选择理由：先并行出多个方案，再一次性对比评分，不能只出一个方案交差
```

```js
export const meta = {
  name: "重构方案对比",
  description: "生成三个不同的重构方案，对比分析后选出最优方案",
  phases: [
    { title: "分析", detail: "分析现状" },
    { title: "生成方案", detail: "并行生成三个不同方案" },
    { title: "对比", detail: "对比评分选最优" },
  ],
}

export default async function () {
  phase("分析")
  const analysis = await agent("分析当前代码的问题", { label: "现状分析" })

  phase("生成方案")
  // 并行生成多个不同风格的方案
  const [planA, planB, planC] = await parallel([
    () => agent(`基于以下分析，设计一个"最小改动"方案：\n${analysis}`, { label: "方案A" }),
    () => agent(`基于以下分析，设计一个"重构"方案：\n${analysis}`, { label: "方案B" }),
    () => agent(`基于以下分析，设计一个"全新"方案：\n${analysis}`, { label: "方案C" }),
  ])

  phase("对比")
  return await agent(
    `对比以下三个方案的可维护性、性能、复杂度、迁移成本，选出最优：\n\nA: ${planA}\n\nB: ${planB}\n\nC: ${planC}`,
    { label: "方案对比", isFinal: true }
  )
}
```

### ⑨ 容错并行（某个失败不阻塞其他）

```
适用：多源搜索（某个源挂了不影响其他）、批量处理、不稳定服务调用
选择理由：多个并行任务中，个别允许失败，成功的仍然需要汇总
```

```js
export const meta = {
  name: "多源容错搜索",
  description: "从多个数据源搜索，失败自动跳过，汇总成功结果",
  phases: [
    { title: "并行搜索", detail: "同时搜索多个源，捕获单个失败" },
    { title: "汇总", detail: "合并所有成功结果" },
  ],
}

export default async function () {
  phase("并行搜索")

  const [a, b, c] = await parallel([
    () => agent("搜索百度", { label: "百度" }).catch(e => { log(`百度失败: ${e.message}`); return null }),
    () => agent("搜索微博", { label: "微博" }).catch(e => { log(`微博失败: ${e.message}`); return null }),
    () => agent("搜索知乎", { label: "知乎" }).catch(e => { log(`知乎失败: ${e.message}`); return null }),
  ])

  phase("汇总")
  const results = [a, b, c].filter(Boolean)
  if (results.length === 0) return await agent("所有源都失败了，给用户友好提示", { label: "无结果提示" })
  return await agent(`综合以下成功结果：\n${results.join("\n---\n")}`, { label: "汇总", isFinal: true })
}
```

## 禁止的反模式
- ❌ 什么任务都用 $dag 包装——纯并行用 parallel，纯串行用 await agent 串联
- ❌ parallel 参数是 Promise 数组（必须是 thunk 数组）
- ❌ agent() 没有 label（调试困难）
- ❌ 所有 agent 用同一个 model（浪费资源）
- ❌ meta.phases 和 phase() 调用不一致
- ❌ 不用 await 包裹 agent() 调用
