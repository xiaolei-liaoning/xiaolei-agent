## 问题 1：`execute_python` sandbox 与 `execute_shell` 的功能冲突（agent 反复被拦）

### 现象
本次日志中 agent 多次试图用 Python 执行小脚本验证（例如 `import subprocess, sys` 跑个校验），每次都被日志里这句打断：
```
2026-09-08 21:24:09,167 | ERROR | 沙盒执行失败: 禁止使用: subprocess（请使用 execute_shell 工具）
```
然后 agent 被迫绕道 `execute_shell`，流程卡顿、多绕好几轮，甚至出现"假完成"。

### 证据（只读核实）
- `core/tools/sandbox_executor.py:333-345` 明确禁止 Python 代码里出现 `subprocess` / `os.system` / `os.popen` / `popen`：
  ```python
  dangerous_imports = ["subprocess", "os.system", "os.popen", "popen"]
  for dangerous in dangerous_imports:
      if dangerous in code:
          raise SecurityError(f"禁止使用: {dangerous}（请使用 execute_shell 工具）")
  ```
- `core/multi_agent_v2/tools/tool_registry.py` 的 `_handle_execute_python` 默认 `sandbox` 模式（docstring：`sandbox 模式：执行后检测文件写入操作`），即走上述禁止逻辑。

### 影响
- agent 的习惯做法（Python 调 subprocess 跑命令）被硬拦，导致其无法顺畅执行验证脚本，被反复打断。
- 这正是本次日志里多处"假完成/空转"的诱因之一。

### 建议方向（待定，不实施）
- **优先级最高、改动最小**：在 `prompts/tools/execute_python.txt` 或 `execute_shell.txt` 描述里明确引导——"验证/执行命令用 execute_shell，不要用 Python subprocess"，让 LLM 少踩坑。（这是改提示词，风险低）
- 或：考虑给 Python 里的 `subprocess` 加可控白名单（如仅允许多进程无害命令），而非一刀切禁止。– 改动较大，需评估安全性。

## 问题 2：子代理 run_react 一路 read_file 空转，逼近轮次上限

### 现象
EverOS 分析日志里，子代理反复显示：
```
[子代理]   ◇ Round 10/15 ──────────────────────────────
[子代理]   ◇ Round 13/15 ──────────────────────────────
```
子代理执行轮次逼近 `15` 上限，说明它在大量 read_file 空转而非高效并行分析。

### 证据（只读核实）
- 子代理复用主代理的 `run_react`（`react_core.py:1203`，`is_subagent` 仅为布尔标记），因此继承了主代理的 read_file 空转倾向。
- `react_core.py:1699-1702` 的"读了≥5个文件就别读了，用 task(explore) 委托子代理"提示**对子代理同样生效**（同一 react_core），但子代理自身就是"探索者"，这条提示对它反而可能无效甚至自我循环。
- 子代理 `max_rounds=15`（`spawn.py:20` `_MAX_SUBAGENT_ROUNDS = 15`），轮次上限较高，进一步放大空转。

### 影响
- 子代理本应为"深度并行分析"，却演变成"逐文件 read_file"的串行低效行为，轮次被空转耗尽，导致"进度 0/0、未完成：最终收尾"。

### 建议方向（待定，不实施）
- 子代理的提示词/工具引导应**有别于主代理**：明确"你是探索者，要快速并行扫多个模块，不要逐个 read_file 深挖"。
- 可考虑给子代理更小的轮次上限（如 10），或强化"读够即产出"约束。

## 问题 3：`进度 0/0 步` —— 子代理/任务的进度追踪为空，无法判断是否完成

### 现象
多处日志末尾：
```
已达轮次上限（15轮）。进度：0/0 步。未完成：最终收尾。
```
进度账目是 `0/0`（空），系统无从判断"到底做完没"，只能靠撞轮次上限强制收尾。

### 证据（只读核实）
- 子代理走纯 ReAct（无 plan），`task_progress` 从未被填充。
- `react_core.py` 的进度判定（`_is_production`、`_has_real_deliverable` 等）只在"agent 声明完成"路径生效；子代理/无 plan 任务下 `task_progress` 恒为 `0/0`，与"交付物是否产出"完全脱节。

### 影响
- 系统无法验证子代理是否真的完成分析，只能依赖轮次上限（15）兜底，导致大量"未完成：最终收尾"的假收尾。

### 建议方向（待定，不实施）
- 给子代理/无 plan 任务也维护一个简易进度（哪怕"已读 N 个文件 / 已产 M 个模块结论"），让收尾判断有据可依。
- 或：当子代理已产出有效分析（result 非空）时，直接判定"完成"，不再看 `task_progress`。
