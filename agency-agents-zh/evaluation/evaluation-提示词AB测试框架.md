================================================================================
提示词名称: 提示词 A/B 测试框架
描述: 系统性框架，用于比较不同的提示词版本，以确定哪个在多个评估标准下产生更好的输出。
使用场景:
  - 测试提示词变体以找到最优版本
  - 比较不同的系统提示词
  - 评估提示词工程技术
  - 针对特定任务优化提示词
================================================================================

<ab_testing_methodology>
步骤 1: 定义假设
- 你想改善什么？（准确性、代码质量、速度、成本）
- 你在测试什么具体变更？
- 你的成功指标是什么？

步骤 2: 创建变体
- 变体 A（对照）: 当前/基线提示词
- 变体 B（实验）: 修改了一个关键变更的提示词
- 保持其他所有条件不变（模型、温度、测试用例）

步骤 3: 设计测试用例
- 创建多样化、有代表性的测试场景
- 包含边界情况和常见情况
- 至少 20-30 个测试用例以获得统计显著性
- 覆盖不同难度级别

步骤 4: 运行实验
- 用两个提示词分别运行每个测试用例
- 随机化顺序以避免偏差
- 使用相同的模型参数
- 记录所有输出和元数据

步骤 5: 评估结果
- 使用评估标准为输出打分
- 计算汇总指标
- 进行统计显著性检验
- 分析成功/失败中的模式

步骤 6: 做出决策
- 如果 B 显著优于 A: 采用 B
- 如果没有显著差异: 保留 A（更简单）
- 如果结果混合: 分析哪些场景有利于哪个版本
</ab_testing_methodology>

<test_design>
样本量:
- 至少 20 个测试用例用于方向性洞察
- 50+ 个测试用例用于统计置信度
- 100+ 用于生产部署决策

测试用例多样性:
- 简单任务（基线性能）
- 复杂任务（能力极限）
- 边界情况（鲁棒性）
- 模糊输入（处理不确定性）
- 不同领域（泛化能力）

控制变量:
- 相同的模型和版本
- 相同的温度和采样参数
- 相同的最大 token 数
- 相同顺序的相同测试用例
- 相同的评估标准
</test_design>

<evaluation_metrics>
定量指标:
- 成功率: 正确完成的任务百分比
- 平均分: 所有输出的平均质量分数
- 延迟: 平均响应时间
- Token 用量: 每次响应的平均 token 数
- 成本: 所有测试用例的总 API 成本

定性指标:
- 代码质量（如果是生成代码）
- 解释的清晰度
- 边界情况的处理
- 错误恢复
- 相似任务间的一致性

统计检验:
- T 检验用于比较均值
- 卡方检验用于成功率差异
- 效应量（Cohen's d）衡量实际显著性
- 置信区间（通常 95%）
</evaluation_metrics>

<prompt_variations_to_test>
结构性变更:
- 添加/移除示例
- 更改指令顺序
- 添加约束或规则
- 修改输出格式要求

内容性变更:
- 不同的人设/角色描述
- 更多/更少的技术语言
- 添加领域特定上下文
- 包含/排除最佳实践

技术性变更:
- 思维链 vs 直接回答
- 少样本 vs 零样本
- 逐步 vs 整体
- 有/无自我反思
</prompt_variations_to_test>

<best_practices>
1. 每次只测试一个变更（隔离变量）
2. 尽可能使用盲评（隐藏是哪个变体）
3. 运行多次迭代以考虑随机性
4. 同时考虑统计显著性和实际显著性
5. 记录所有测试参数以保证可复现性
6. 关注失败中的模式，而非仅看汇总分数
7. 考虑成本效益权衡（轻微改善 vs 2 倍成本）
8. 在生产级数据上测试，而非玩具示例
</best_practices>
