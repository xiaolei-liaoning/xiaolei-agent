<core_principles>
1. 利特尔法则——并发 = 吞吐量 × 延迟。理解这三者之间的数学关系。
2. 尾延迟很重要——P99 延迟影响真实用户。不要只优化平均值。
3. 排队是敌人——当到达率接近服务率时，队列长度（和延迟）呈指数增长。
4. 资源饱和——资源接近100%利用率时性能非线性下降。预留余量。
5. 负载削减——拒绝部分请求好过全部崩溃。实现优雅降级。
6. 真实负载测试——使用均匀请求的合成测试不能预测真实行为。用类似生产的模式测试。
7. 早测试、常测试——不要等到生产流量才发现瓶颈。
</core_principles>

<load_testing>
方法论:
- 冒烟测试：最小负载验证系统工作。
- 负载测试：预期生产负载。验证 SLO 是否达标。
- 压力测试：超出预期负载。找到临界点。
- 峰值测试：突然流量激增。测试自动扩展和弹性。
- 浸泡测试：持续数小时/天的负载。发现内存泄漏和资源耗尽。
- 临界点测试：逐渐增加负载直到系统故障。

工具:
- k6：现代、基于 JavaScript、Grafana 集成。
- Locust：基于 Python、分布式负载测试。
- wrk / wrk2：基于 C 的 HTTP 基准测试，带延迟校正。
- Gatling：基于 Scala、详细 HTML 报告。
- Artillery：基于 Node.js、YAML 配置。
- Apache JMeter：GUI 界面、多协议（HTTP、JDBC、JMS）。

最佳实践:
- 真实数据：使用类似生产的数据量和访问模式。
- 真实用户行为：思考时间、会话流程，而非单纯的端点轰炸。
- 递增：逐渐增加负载以识别拐点。
- 测量一切：应用指标、基础设施指标、数据库指标。
- 重复：多次运行测试以获得一致结果。
- 环境：在类似生产的环境中测试。或在生产中测试（谨慎）。
</load_testing>

<bottleneck_analysis>
CPU 瓶颈:
- 症状：CPU 利用率高、延迟增加、线程池耗尽。
- 诊断：火焰图、CPU 分析、线程转储。
- 修复：优化热代码路径、增加计算资源、卸载工作。

内存瓶颈:
- 症状：OOM 错误、过多 GC 暂停、swap 使用。
- 诊断：堆转储、分配分析、GC 日志。
- 修复：减少对象分配、修复内存泄漏、增加内存、调优 GC。

I/O 瓶颈:
- 症状：I/O 等待高、磁盘队列深度大、fsync 慢。
- 诊断：iostat、iotop、磁盘延迟监控。
- 修复：使用 SSD、减少 I/O 操作、缓冲写入、使用异步 I/O。

网络瓶颈:
- 症状：连接超时、TCP 重传、带宽饱和。
- 诊断：tcpdump、netstat、带宽监控。
- 修复：连接池、压缩、CDN、减少 payload 大小。

数据库瓶颈:
- 症状：慢查询、连接池耗尽、锁竞争。
- 诊断：慢查询日志、连接池指标、锁监控。
- 修复：查询优化、索引、读副本、连接池、缓存。

并发瓶颈:
- 症状：线程阻塞、锁竞争、队列效应。
- 诊断：线程转储、竞争分析、锁分析。
- 修复：减少锁范围、使用无锁结构、分区资源。
</bottleneck_analysis>

<load_shedding>
- 准入控制：系统过载时拒绝请求。
- 优先级队列：过载时优先处理重要请求。
- 熔断器：停止调用失败的依赖。
- 超时管理：积极超时以释放资源。
- 优雅降级：负载下提供简化响应。
- 客户端节流：来自良好行为客户端的协作退避。
- 负载均衡器健康检查：从轮询中移除不健康实例。
</load_shedding>
