<core_principles>
1. 一切即代码 — 基础设施、配置、策略和密钥管理——全部用代码定义，版本控制，同行评审。
2. 不可变基础设施 — 不要修补运行中的系统。用从代码构建的新系统替换。
3. 幂等运行 — 运行两次自动化应产生相同结果。可以安全重试。
4. 测试基础设施 — 在应用到生产之前验证基础设施代码。Lint、计划审查、集成测试。
5. 模块化和可复用 — 构建可组合的基础设施模块。不要复制粘贴基础设施代码。
6. 状态管理 — 小心管理 Terraform 状态: 远程后端、锁、访问控制。
7. 漂移检测 — 持续检查与代码偏离的手动变更。告警并调和。
</core_principles>

<terraform>
结构:
- 模块: 可复用的基础设施组件（VPC、EKS 集群、数据库）。
- 根模块: 特定于环境的模块组合。
- 变量: 为不同环境参数化模块。
- 输出: 暴露跨模块引用的值。

状态管理:
- 远程后端: S3+DynamoDB (AWS)、GCS (GCP)、Terraform Cloud。
- 状态锁: 防止并发修改。
- 状态隔离: 每个环境和组件独立状态。
- Import: 将现有资源纳入 Terraform 管理。
- 状态操作: terraform state mv、rm 用于重构。

最佳实践:
- 锁定提供商版本: 防止意外的破坏性变更。
- 使用数据源: 引用现有资源而不管理它们。
- 动态块: 以编程方式生成重复配置。
- 使用 Workspace 或基于目录的隔离来区分环境。
- Terragrunt: 跨多个根模块的 DRY 配置。
- Pre-commit hooks: terraform fmt、terraform validate、tflint。

测试:
- terraform plan: 应用前审查变更。
- tflint: 常见错误的 lint 规则。
- Checkov / tfsec: 安全策略扫描。
- Terratest: 基于 Go 的集成测试，配置和验证真实基础设施。
- OPA / Sentinel: 用于基础设施合规的策略即代码。
</terraform>

<configuration_management>
Ansible:
- 无代理: 基于 SSH，无需安装客户端。
- Playbook: YAML 定义的配置任务。
- Role: 可复用的任务、handler 和模板包。
- Inventory: 来自云提供商的动态 inventory。
- 幂等模块: 确保期望状态无副作用。
- 用途: 初始配置、软件安装、临时操作。

Packer:
- 从代码构建机器镜像（AMI、GCP Image、Docker）。
- Provisioner: shell 脚本、Ansible、Chef 用于镜像配置。
- 多构建器: 从一个模板为多个平台构建。
- 用途: 不可变基础设施——将所有内容烘焙到镜像中。
</configuration_management>

<automation_patterns>
自愈:
- 健康检查自动检测故障。
- 自动替换: 不健康的实例无需干预即可被替换。
- 自动弹性: 基于需求伸缩资源。
- 断路器: 隔离故障组件以防止级联。
- 自动回滚: 故障时回滚到上一个已知正常状态。

配置工作流:
- GitOps: 通过 pull request 进行基础设施变更。
- Terraform Cloud / Atlantis: 在 PR 上自动执行 plan-and-apply。
- 基于流水线: 用于基础设施变更的 CI/CD 流水线。
- 审批门禁: 生产变更需要人工审批。
- 漂移检测: 定时运行以检测手动变更。

多环境:
- 环境一致性: 相同的基础设施定义，不同的参数。
- 推进: 变更经过 dev → staging → production。
- 功能环境: 用于功能分支的临时环境。
- 资源命名: 跨环境一致的命名约定。
</automation_patterns>
