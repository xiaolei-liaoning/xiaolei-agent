<core_principles>
1. 缓存正确的内容——不是所有东西都应该被缓存。缓存读取频繁、计算昂贵且能容忍一定过时的数据。
2. 显式失效策略——对每个缓存项，在缓存之前定义它何时以及如何被失效。"只设个 TTL" 对重要数据来说不是策略。
3. 让缓存更靠近用户——将缓存数据尽可能靠近消费者: 浏览器缓存 → CDN → 反向代理 → 应用缓存 → 数据库缓存。
4. TTL 是你的安全网——即使有主动失效也要设置 TTL。TTL 在失效失败时防止过时数据无限期保留。
5. 衡量缓存有效性——跟踪命中率、未命中率、驱逐率和延迟。命中率 < 80% 的缓存可能不值得其复杂度。
6. 为缓存故障做计划——缓存完全宕机时应用必须能工作（可能变慢）。缓存是优化，不是依赖。
7. 警惕缓存踩踏——当热门缓存项过期时，数百个请求可能同时击中数据库。要有预防策略。
</core_principles>

<caching_layers>
浏览器缓存:
- Cache-Control 头用于静态资源: max-age=31536000、immutable（配合文件名内容哈希）。
- ETag 和 Last-Modified 用于条件请求（304 Not Modified）。
- Service Worker 缓存用于离线优先 PWA。
- sessionStorage/localStorage 用于客户端数据缓存。

CDN 缓存:
- 静态资源（JS、CSS、图片、字体）: 配合内容哈希的激进缓存。
- 动态内容: 较短 TTL，Vary 头用于个性化内容。
- 地理分布降低全球延迟。
- Purge API 用于特定 URL 的即时失效。
- Stale-while-revalidate: 在后台获取新鲜内容时提供过时内容。

反向代理缓存（Nginx、Varnish）:
- 匿名/公开内容的全页缓存。
- 基于键的 API 响应缓存。
- 微缓存: 1-5 秒缓存用于高流量端点（吸收峰值）。
- 缓存键设计: URL + 相关头/cookie（避免过度键控）。

应用缓存（Redis、Memcached）:
- 查询结果缓存: 用领域特定键缓存数据库查询结果。
- 计算值缓存: 缓存昂贵的计算、聚合、转换。
- 会话缓存: 将用户会话存储在 Redis 中实现无状态应用服务器。
- 速率限制: 基于 Redis 的令牌桶或滑动窗口计数器。

数据库缓存:
- 查询计划缓存: 数据库缓存执行计划（使用预编译语句）。
- 缓冲池: 数据库在内存中缓存频繁访问的页面。
- 物化视图: 按计划刷新的预计算查询结果。
- 结果集缓存: 某些数据库缓存查询结果（MySQL 查询缓存——谨慎使用）。
</caching_layers>

<caching_patterns>
Cache-aside（惰性加载）:
- 应用检查缓存 → 命中则返回。未命中则查询数据库，存入缓存，返回。
- 最常见模式。适合读密集型工作负载。
- 风险: 缓存未命中惩罚（首次请求比无缓存更慢）。

Write-through:
- 应用同时写入缓存和数据库。
- 缓存始终与数据库一致。
- 风险: 写入延迟增加（写入两个地方）。

Write-behind（Write-back）:
- 应用写入缓存。缓存异步写入数据库。
- 写入快，数据库最终一致。
- 风险: 缓存在写入数据库前崩溃会导致数据丢失。

Read-through:
- 缓存负责在未命中时从数据库加载数据。
- 应用只与缓存交互，不直接与数据库交互。
- 应用代码更干净但与缓存基础设施耦合更紧。

Refresh-ahead:
- 缓存在条目过期前主动刷新。
- 用户永远不会在热门项目上遇到缓存未命中。
- 实现: 后台任务在 TTL 的 80% 时刷新条目。
</caching_patterns>

<cache_invalidation>
基于 TTL:
- 简单: 为每个缓存项设置过期时间。
- 权衡: 数据库更新和缓存过期之间的过时窗口。
- 适用: 轻微过时可接受的数据（产品列表、用户资料）。

基于事件:
- 数据变更时发布失效事件（数据库触发器、应用事件）。
- 订阅事件并失效/更新缓存项。
- 适用: 一致性重要的数据（库存数量、订单状态）。

基于版本:
- 在缓存键中包含版本号: user:123:v5。
- 更新时递增版本。旧缓存项自然变得不再使用。
- 适用: 有复杂失效模式的数据。

基于标签:
- 为缓存项分配标签: product:123 标记为 [category:electronics, brand:apple]。
- 按标签失效: 类别变更时，失效该类别标记的所有项。
- 适用: 有共享依赖的数据（类别页缓存、搜索结果缓存）。
</cache_invalidation>

<common_problems>
缓存踩踏:
- 问题: 热门键过期，许多请求同时查询数据库。
- 方案 1: 基于锁——第一个请求获取锁，其他等待。
- 方案 2: 概率性提前重计算——在实际过期前刷新。
- 方案 3: Stale-while-revalidate——在后台刷新时提供过时数据。

冷启动:
- 问题: 部署或重启后缓存为空导致高数据库负载。
- 方案: 缓存预热——部署期间用频繁访问的数据预填充缓存。
- 方案: 金丝雀部署的渐进流量提升。

缓存穿透:
- 问题: 对不存在数据的查询总是未命中缓存，击中数据库。
- 方案: 缓存负结果（null 值）配合短 TTL。
- 方案: Bloom 过滤器在查询数据库前检查键是否存在。

热键:
- 问题: 单个缓存键接收到不成比例的流量。
- 方案: 将热键复制到多个缓存节点。
- 方案: 对超热键使用本地进程内缓存。
</common_problems>
