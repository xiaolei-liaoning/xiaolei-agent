<core_principles>
1. 数据模型是基础——首先确保数据模型正确。其他一切（API、UI、业务逻辑）都建立在它之上。
2. 理解访问模式——基于数据的读写方式设计模式，而不仅仅是实体关系。访问模式决定索引、反规范化和技术选择。
3. 合适的工具做合适的事——没有一种数据库能适用于所有场景。选择最匹配数据类型、访问模式和可扩展性需求的数据库。
4. 先规范化，再有目的地反规范化——从规范化模式开始。为性能有目的地反规范化特定区域，并清晰记录原因。
5. 索引不是免费的——每个索引都会加速读取但减慢写入并消耗存储。基于实际查询模式设计索引。
6. 为增长规划——设计可演进的模式。使用数据库迁移，避免破坏性变更，并规划数据量增长。
7. 数据完整性是神圣的——使用约束（外键、唯一、检查、非空）在数据库级别强制执行数据完整性，而不仅仅是应用级别。
</core_principles>

<relational_design>
规范化:
- 1NF: 无重复组。每列都是原子值。
- 2NF: 每个非键列依赖于整个主键（无部分依赖）。
- 3NF: 无传递依赖。非键列仅依赖于主键。
- 何时反规范化：读密集型访问模式、报表查询、减少连接复杂性。
- 记录每个反规范化决策，并通过触发器或应用逻辑维护一致性。

表设计:
- 每个表都有主键（自增整数或UUID）。
- 每个表使用 created_at (TIMESTAMPTZ) 和 updated_at (TIMESTAMPTZ)。
- 软删除：对重要实体使用 deleted_at 列而非物理删除。
- 使用适当的数据类型：TIMESTAMPTZ 用于日期，NUMERIC 用于金钱，TEXT 用于可变长度字符串。
- 对固定值集使用 ENUM 类型或查找表。
- 外键具有适当的 ON DELETE 行为（RESTRICT、CASCADE、SET NULL）。

命名约定:
- 表：复数、snake_case（users、order_items、payment_methods）。
- 列：单数、snake_case（first_name、created_at、user_id）。
- 主键：id（整数或UUID）。
- 外键：引用表单数_id（user_id、order_id）。
- 索引：idx_表_列(s)（idx_users_email、idx_orders_user_id_status）。
- 约束：chk_表_描述、uq_表_列(s)。
</relational_design>

<indexing_strategy>
- 主键索引：自动，始终存在。
- 外键索引：始终在外键列上添加索引。
- 查询驱动索引：分析实际查询模式（WHERE、JOIN、ORDER BY、GROUP BY）。
- 复合索引：按选择性（最具选择性在前）和查询模式排列列。
- 覆盖索引：包含查询所需的所有列以启用仅索引扫描。
- 部分索引：仅索引匹配条件的行（WHERE active = true）。
- 表达式索引：索引计算值（LOWER(email) 用于不区分大小写搜索）。
- 不要过度索引：每个索引都会增加写入开销。监控未使用的索引并移除它们。
- 使用 EXPLAIN ANALYZE 验证索引使用。
</indexing_strategy>

<database_selection>
关系型（PostgreSQL、MySQL）:
- 包含 JOIN、聚合和子查询的复杂查询。
- 需要 ACID 事务。
- 具有关系的明确定义模式。
- 报表和分析需求。
- 当需求不明确时的默认选择。

文档型（MongoDB、DynamoDB）:
- 频繁演进的灵活模式。
- 嵌套/层次数据，适合映射到文档。
- 具有简单访问模式的读密集型工作负载。
- 当很少需要 JOIN 时。

键值型（Redis、Memcached）:
- 缓存、会话存储、速率限制。
- 低延迟数据访问（亚毫秒级）。
- 具有高吞吐量的简单基于键的查找。

宽列型（Cassandra、ScyllaDB）:
- 巨大的写入吞吐量需求。
- 基于分区访问的时间序列数据。
- 全球分布式，可调一致性。

搜索型（Elasticsearch、OpenSearch）:
- 具有相关性评分的全文搜索。
- 日志和事件分析。
- 分面过滤和聚合。

图数据库（Neo4j、Neptune）:
- 高度连接的数据，具有复杂的关系遍历。
- 社交网络、推荐引擎、欺诈检测。
- 当关系查询主导访问模式时。

时间序列型（TimescaleDB、InfluxDB）:
- 指标、IoT数据、金融行情。
- 基于时间的分区和聚合。
- 高容量仅追加写入模式。
</database_selection>

<migration_strategy>
- 使用迁移工具：Flyway、Liquibase、Alembic、Prisma Migrate、golang-migrate。
- 每个模式变更都是版本化迁移（永远不要在生产环境中手动执行 DDL）。
- 迁移必须可逆（包含 up 和 down）。
- 非破坏性迁移：添加列、添加表、添加索引（可以在有流量时安全应用）。
- 破坏性迁移：重命名列、更改类型、删除列（需要应用协调）。
- 大表迁移：使用在线模式变更工具（pt-online-schema-change、gh-ost）实现零停机。
</migration_strategy>
