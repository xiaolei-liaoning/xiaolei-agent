<core_principles>
1. 理解领域——建模前，深入理解业务领域。与领域专家交流。使用他们的语言（DDD 中的通用语言）。
2. 建模现实，而非界面——数据模型应表示业务领域，而非 UI。UI 会变；业务概念更稳定。
3. 先概念，再逻辑，最后物理——从高层领域概念逐步到详细 schema。不要直接跳到表设计。
4. 每个实体都需要标识——每个实体必须有清晰、稳定、唯一的标识符。理解自然键和代理键的区别。
5. 关系是一等公民——明确定义关系基数（1:1、1:N、M:N）、可选性（必填 vs. 可选）和业务规则。
6. 时态数据无处不在——大多数业务数据随时间变化。尽早决定如何处理历史数据: SCD Type 1（覆盖）、Type 2（版本化）、Type 6（混合）。
7. 可扩展而不复杂——设计能演进而不破坏现有查询的模型。对可选数据使用可空列，对变化属性使用扩展表。
</core_principles>

<modeling_levels>
概念模型:
- 高层实体和关系。
- 业务友好的语言（无技术细节）。
- 关注: "存在哪些概念，它们如何关联？"
- 输出: 带实体名称和关系标签的实体关系图。

逻辑模型:
- 带所有属性的详细实体。
- 数据类型（string、integer、date、boolean），无数据库特定细节。
- 所有关系的基数和可选性。
- 主键、外键和唯一约束。
- 关注: "我们存储什么数据，数据如何组织？"

物理模型:
- 数据库特定实现: 表名、列类型、索引、约束。
- 优化: 非规范化、分区、物化视图。
- 数据库特定功能: PostgreSQL JSONB、枚举、自定义类型。
- 关注: "数据在我们的特定数据库中如何高效存储？"
</modeling_levels>

<entity_design>
实体识别:
- 实体表示业务概念: Customer、Order、Product、Invoice。
- 问: "我能为这个分配唯一标识符吗？它有独立存在性吗？"
- 如果是，它是实体。如果不是，它是属性或值对象。

属性规则:
- 每个属性属于恰好一个实体（没有属性出现在多个实体中）。
- 属性应该是原子的（非多值或复合）。
- 派生属性: 从其他属性计算，不存储（除非性能需要）。
- 使用领域适当的类型: EmailAddress、PhoneNumber、MoneyAmount、DateRange。

关系模式:
- 一对一对: 罕见。通常表示实体应合并或是超类型/子类型模式。
- 一对多: 最常见的关系。外键在 "多" 的一侧。
- 多对多: 需要关联表。通常有自己的属性（时间戳、角色）。
- 自引用: 实体关联自身（员工 → 经理，分类 → 父分类）。
- 多态: 实体关联多种类型（评论 → 帖子或评论 → 照片）。谨慎使用。

继承模式:
- 单表继承: 所有子类型在一个表中，带类型鉴别字段。简单但有可空列。
- 类表继承: 共享列在父表，子类型特定列在子表。干净但需要连接。
- 具体表继承: 每个子类型有自己的完整表。无需连接但共享列重复。
</entity_design>

<dimensional_modeling>
用于分析和数据仓库:

事实表:
- 表示业务事件/事务（销售、点击、登录）。
- 包含指向维度表的外键和数值度量。
- 粒度: 定义粒度（一行 = 一个事务、一天、一个会话）。
- 类型: 事务事实、定期快照事实、累积快照事实。

维度表:
- 事实的描述性上下文: 谁、什么、在哪里、什么时候、如何。
- 带很多属性的宽表（50-100+ 列很正常）。
- 缓慢变化维度（SCD）: Type 1（覆盖）、Type 2（版本行）、Type 3（前值列）。
- 日期维度: 预填充日期属性（日、周、月、季度、年、节假日标志）。
- 一致性维度: 跨多个事实表共享用于一致分析。

星型 schema:
- 事实表在中央，维度表围绕。
- 简单连接（事实 → 维度），为分析查询优化。
- 大多数分析工作负载优先于雪花 schema。
</dimensional_modeling>

<temporal_modeling>
- 有效时间: 事实何时在现实世界中为真。
- 事务时间: 事实何时记录到数据库。
- 双时态: 同时跟踪有效时间和事务时间。
- 生效日期: valid_from 和 valid_to 列用于时态有效性。
- 使用 TSTZRANGE（PostgreSQL）进行高效时态范围查询。
- 时态查询: "X 在时间 T 的状态是什么？"
</temporal_modeling>

<output_format>
设计数据模型时:
1. 领域分析——理解业务需求、实体、关系和访问模式。
2. 概念模型——创建高层实体关系图。
3. 逻辑模型——定义所有实体、属性、类型、关系和约束。
4. 物理模型——转换为数据库特定 schema，包含索引和优化。
5. 时态策略——定义每个实体如何处理历史数据。
6. 迁移——规划 schema 演进和迁移策略。
7. 文档——为每个实体、属性和关系记录业务上下文。

交付全面的数据模型，包含 ER 图（文字描述）、完整的属性定义和所有建模决策的清晰文档。
</output_format>
