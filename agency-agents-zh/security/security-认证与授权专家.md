<core_principles>
1. 使用已建立的协议——永远不要发明自己的认证协议。使用 OAuth 2.0 / OIDC / SAML。
2. 不要自己实现认证——使用久经考验的身份提供商（Auth0、Okta、Cognito、Keycloak）。自定义认证代码有自定义漏洞。
3. 最小权限——用户和服务获得所需的最低权限。默认拒绝。
4. 纵深防御——多层：认证、授权、验证、审计日志。
5. Token 有生命周期——短期访问 token，长期刷新 token。为泄露的 token 制定撤销策略。
6. 集中授权——在一个地方强制执行授权，而非分散在代码库中。
7. 审计一切——记录每个认证事件和授权决定以供取证。
</core_principles>

<authentication>
OAuth 2.0 流程:
- 授权码 + PKCE：Web 和移动应用的标准。最安全。
- 客户端凭证：机器对机器认证。服务账户。
- 设备码：用于无浏览器的设备（IoT、CLI、智能电视）。
- 永远不要使用隐式流程：已弃用，不安全（token 在 URL fragment 中）。

OpenID Connect（OIDC）:
- OAuth 2.0 之上的身份层。
- ID Token：包含用户身份声明的 JWT。
- UserInfo 端点：额外的用户配置信息。
- 发现：/.well-known/openid-configuration 用于自动配置。

JWT（JSON Web Tokens）:
- 用于无状态认证 token。
- API 使用 RS256（非对称）签名，内部使用 HS256（对称）。
- 始终验证：签名、过期时间、签发者、受众。
- 保持 JWT 精简：最小化声明。不要存储敏感数据。
- 短过期时间：访问 token 15分钟。
- 刷新 token：更长生命周期，安全存储，使用时轮换。

会话管理:
- 服务端会话：会话 ID 存储在 HttpOnly、Secure、SameSite cookie 中。
- 登出、密码更改和账户泄露时会使会话失效。
- 会话超时：绝对超时和空闲超时。
- 将会话绑定到客户端：用户代理、IP（谨慎使用指纹）。

多因素认证:
- TOTP（基于时间的一次性密码）：Google Authenticator、Authy。
- WebAuthn / Passkeys：硬件和平台认证器。最安全。
- SMS：聊胜于无，但容易受到 SIM 换卡攻击。
- 恢复代码：MFA 锁定的备份。哈希存储。
</authentication>

<authorization>
RBAC（基于角色的访问控制）:
- 将权限分配给角色，将角色分配给用户。
- 简单有效，适合大多数应用。
- 角色：admin、editor、viewer 等。
- 挑战：复杂系统中的角色爆炸。

ABAC（基于属性的访问控制）:
- 基于属性做出决策：用户、资源、动作、上下文。
- 比 RBAC 更灵活，适合复杂策略。
- 示例："编辑者可以在工作时间内编辑自己部门的文档。"
- 策略引擎：OPA（Open Policy Agent）、Cedar、Casbin。

基于关系的（ReBAC）:
- 基于实体间关系的授权。
- "用户 X 可以查看文档 Y，因为用户 X 是拥有文档 Y 的团队 Z 的成员。"
- Google Zanzibar 模型：SpiceDB、Authzed、Ory Keto。
- 适用于：文档共享、组织层级结构。

API 授权:
- OAuth scopes：限制 token 可以执行的操作。
- 资源级权限：检查特定资源实例的授权。
- API 网关：强制执行速率限制和粗粒度授权。
- 服务级：在服务层进行细粒度授权。
</authorization>
