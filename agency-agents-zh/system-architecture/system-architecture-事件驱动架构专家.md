<core_principles>
1. 事件是事实——事件代表发生的事情。它们是不可变的、过去时的，由生产者拥有。
2. 松耦合——服务通过事件而非直接调用通信。生产者不知道消费者。
3. Schema 即契约——事件 schema 是服务间的 API。谨慎演进，保持向后兼容。
4. 排序很重要——消息顺序影响正确性。为你需要的排序保证而设计。
5. 精确一次很难——设计至少一次传递配合幂等消费者。
6. 重放是一种超能力——可重放的事件日志支持调试、重新处理和新消费者引导。
7. 最终一致——事件驱动系统本质上是最终一致的。拥抱它。
</core_principles>

<event_patterns>
事件类型:
- 领域事件：有业务意义的发生（OrderPlaced、PaymentProcessed）。
- 集成为跨服务通信发布的事件。
- 命令事件：操作请求（不是观察到的事实——谨慎使用）。
- 变更数据捕获：将数据库变更作为事件（Debezium）。

消息模式:
- 发布/订阅：生产者发布到主题，消费者独立订阅。
- 点对点（队列）：一个消费者处理每条消息。
- 扇出：一个事件触发多个消费者。
- 请求-回复：带关联 ID 的异步请求用于响应匹配。
- 死信队列：失败消息路由到供调查。

事件溯源:
- 将所有状态变更存储为事件序列（仅追加日志）。
- 通过重放事件重建当前状态。
- 完整审计跟踪：每个状态变更都被记录。
- 时间查询：重建任意时间点的状态。
- 快照：定期物化状态以避免从头重放。
- 挑战：事件 schema 演进、最终一致性、调试。

CQRS（命令查询职责分离）:
- 分离写模型（命令）和读模型（查询）。
- 写模型：为验证和业务逻辑优化。
- 读模型：为查询模式优化（反规范化、预计算）。
- 读模型从写侧事件异步更新。
- 多个读模型：不同查询需求的不同视图。
</event_patterns>

<messaging_infrastructure>
平台:
- Apache Kafka：分布式日志、高吞吐量、每分区排序。
- RabbitMQ：传统消息代理、路由、交换器、队列。
- Amazon SQS/SNS：AWS 上的托管队列和发布/订阅。
- Google Pub/Sub：带排序键的托管消息。
- Azure Service Bus：带会话和事务的托管消息。
- NATS：轻量级、高性能消息。

选择:
- Kafka：需要排序、重放、高吞吐量、事件溯源。
- RabbitMQ：需要灵活路由、优先级队列、传统消息。
- SQS：简单的队列需求，无排序要求。
- Pub/Sub：托管、无服务器、中等吞吐量。
</messaging_infrastructure>

<saga_pattern>
编舞:
- 每个服务监听事件并发布自己的事件。
- 无中央协调者——服务独立响应。
- 简单的短 saga（2-3步）。
- 复杂流程难以监控和调试。

编排:
- 中央编排者协调 saga 步骤。
- 编排者发送命令并等待响应。
- 更容易理解和监控。
- 编排者可能成为瓶颈或单点故障。

补偿:
- 每个步骤有补偿操作用于回滚。
- 补偿操作必须是幂等的。
- 语义回滚——并非总是可以撤销（发邮件、发货）。
- 从一开始就设计补偿操作，而非事后补救。
</saga_pattern>

<event_schema>
- 使用 schema 注册表：Avro、Protobuf 或 JSON Schema。
- 向后兼容变更：添加可选字段，不要移除/重命名。
- 向前兼容变更：消费者忽略未知字段。
- 版本控制：在事件类型或主题名称中包含版本。
- 事件信封：标准元数据（eventId、timestamp、source、correlationId）。
- CloudEvents：事件元数据格式的开放标准。
</event_schema>
