## 一、技术栈兼容性

### 1.1 声明栈 vs 实际使用栈

| 类别 | pyproject.toml 声明 | 实际代码使用 | 兼容性 |
|------|--------------------|--------------|--------|
| Web 框架 | FastAPI ≥0.115 / uvicorn | FastAPI + WebSocket + CORS + 静态文件 | ✅ 一致 |
| Python | ≥3.13 | 全程 asyncio、dataclass、asynccontextmanager | ✅ 一致 |
| 数据库 | Redis / PyMySQL / SQLAlchemy 2.0 | 用户管理、会话存储 | ✅ 一致 |
| LLM | zhipuai ≥2.0、httpx | 智谱 GLM 接入 | ✅ 一致 |
| 向量库 | chromadb / sentence-transformers / transformers / torch | 语义检索、Embedding | ✅ 一致（torch 体积大） |
| 浏览器 | playwright | GUI/网页自动化 | ✅ 一致 |
| macOS GUI | PyObjC / PyAutoGUI / pyperclip | 桌面自动化 | ✅ 一致 |
| 数据分析 | pandas / matplotlib / scikit-learn / lightgbm | 数据任务 | ✅ 一致 |
| OCR（可选） | paddleocr / paddlepaddle（optional ocr） | OCR 能力 | ✅ 已隔离为可选 |
| 工具 | dotenv / pyyaml / pyjwt / loguru / psutil | 系统监控、日志 | ✅ 一致 |

### 1.2 兼容性亮点
- **OCR/重依赖已用 `[project.optional-dependencies]` 隔离**（dev / ocr），避免拖慢核心安装。
- 版本约束均带下限（`>=`），未锁死，升级空间良好。
- `uv.lock` 存在，说明采用 uv 锁文件管理，可复现性强。

### 1.3 潜在兼容性风险
| 风险项 | 说明 | 建议 |
|--------|------|------|
| **torch 全量依赖** | 即便不用 GPU 也会随 chromadb 一起安装，体积巨大 | 考虑 CPU-only wheel 或按需加载 |
| **PyObjC 绑定 macOS** | 声明在通用依赖中，Linux 部署会失败 | 移入 optional 或平台条件标记 |
| **Python 3.13 较新** | 部分 C 扩展依赖可能滞后 | 部署前做全量 import 冒烟测试 |
| **双架构并存** | V1 与 V2 依赖栈不同，可能引入隐性冲突 | 明确版本边界，统一依赖入口 |

## 二、项目成熟度判断

### 2.1 成熟度评级：**高（生产级 / 接近 GA）**

依据：
1. **版本号 3.4.0** 且语义化递增，说明历经多轮迭代。
2. **双架构演进（V1 → V2）**：V1（core/agent_system）完整可用且有测试覆盖；V2（core/multi_agent_v2）为新一代 ReAct + 中间件 + 编排引擎，处于演进升级期。
3. **工程化配套齐全**：
   - `.pre-commit-config.yaml`（代码规范门禁）
   - `pyrightconfig.json`（静态类型检查）
   - `pytest` + `pytest-asyncio`（测试体系）
   - `Dockerfile`（容器化）
   - `.github/workflows`（CI/CD）
   - `.env.example` / `.env.free_llm`（多环境配置模板）
4. **文档资产丰富**：README、多份架构分析 / 状态报告 / 测试报告、`AGENTS.md`。

### 2.2 架构成熟度体现
- **分层清晰**：用户交互层（CLI/Web API）→ 核心引擎层（core）→ MCP 服务层（功能 MCP 21 个 + 外部 MCP + Skill MCP）。
- **生命周期规范**：已从旧 `on_event` 迁移到 `asynccontextmanager` 的 lifespan 模式。
- **依赖注入**：采用 `AppContext` 数据类容器管理全局状态。
- **中间件链**：请求日志中间件 + V2 的 14 层 Agent 中间件（权限→记忆→预算）。
- **记忆体系**：短期记忆（文件）+ 向量记忆 + 用户画像三层。

### 2.3 尚存的不成熟点
| 方面 | 现状 | 判断 |
|------|------|------|
| V1/V2 双架构 | 并存运行 | 存在技术债，需明确迁移路线 |
| 顶层文件冗余 | 根目录存在多份分析/报告 md 与 html | 建议归档至 docs/ |
| 残留杂项 | `nul`、`error_log.txt`、`report_null.html` | 疑似调试残留，应清理 |
| GUI 自动化 | macOS 专用 | 平台耦合，跨平台受限 |

## 三、缺失组件识别

### 3.1 功能性缺失
| 缺失项 | 说明 | 优先级 |
|--------|------|--------|
| **可观测性集成** | 依赖 loguru/psutil 自建，缺 Prometheus/OpenTelemetry 标准链路 | 高 |
| **鉴权加固** | CORS `allow_origins=["*"]` + `allow_credentials=True` 组合存在安全风险 | 高 |
| **限流/熔断** | 未见显式 API 限流与 LLM 调用熔断机制 | 高 |
| **配置中心化** | 散落 .env 多套，缺统一配置校验/热更新 | 中 |
| **测试覆盖缺口** | 有测试体系但需确认 V2 编排/中间件覆盖 | 中 |

### 3.2 工程化缺失
| 缺失项 | 说明 |
|--------|------|
| 依赖安全审计 | 未见 bandit / pip-audit / SCA 集成 |
| 许可证合规清单 | 依赖众多，缺第三方 LICENSE 汇总 |
| 变更日志 | 未见 CHANGELOG.md 自动化 |
| 性能基准 | 缺压测（load test）脚本与基准数据 |

## 四、扩展建议

### 4.1 短期（1–2 周）
1. **修复 CORS 安全配置**：开发期放宽但生产环境收敛 `allow_origins`，避免 `*` + credentials。
2. **清理顶层杂项**：归档多份分析 md/html 至 `docs/`，删除 `nul`、`error_log.txt`、`report_null.html` 等残留。
3. **补充核心冒烟测试**：Python 3.13 + 全依赖 import 测试，确保新增环境可启动。

### 4.2 中期（1–2 月）
1. **制定 V1→V2 迁移路线图**：明确 V2 覆盖 V1 的时间点与兼容层，收敛双架构技术债。
2. **引入 OpenTelemetry + Prometheus**：统一 trace/metric，替代自建监控。
3. **平台解耦**：将 PyObjC/PyAutoGUI 移入 optional，Linux 部署无阻塞。

### 4.3 长期（季度级）
1. **API 限流与熔断**：为 LLM 调用与外部 MCP 增加令牌桶限流 + 熔断降级。
2. **LLM 网关抽象**：当前绑定 zhipuai，建议抽象统一 LLM Provider 接口，便于接入多模型。
3. **依赖瘦身**：评估 torch 按需加载，降低安装体积与启动时间。
4. **发布流程**：接入 CHANGELOG + 语义化发布 + 依赖安全审计门禁。
