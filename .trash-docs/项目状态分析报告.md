## 二、核心代码解读（main.py）

- **日志**：`logging.basicConfig` 统一 INFO 级别。
- **生命周期**：使用现代 `lifespan` asynccontextmanager（替代弃用的 `on_event`），启动时：
  1. 调用 `SystemInitializer(app, ctx).initialize()`
  2. 启动 WebSocket 心跳检测（`api/routes/chat_ws.manager`）
  3. 初始化文件 watcher（`core/watcher_setup`）
  4. shutdown 时对称地停止心跳与 watcher
- **FastAPI 应用**：`title` / `version` / `description` 配置完整。
- **CORS**：`allow_origins=["*"]` + `allow_credentials=True`（开发用宽松策略）。
- **静态文件**：挂载 `static/` 目录。
- **路由策略**：页面路由统一由 `api/pages.py` 提供，main.py 不重复注册。
- **全局状态**：采用 `AppContext` dataclass 依赖容器模式。
- **启动**：支持 `DEV_MODE` 环境变量控制热重载（`api/core/tools` 目录）。

## 三、识别出的潜在问题

### 🔴 高危
1. **CORS 配置过松**：`allow_origins=["*"]` 搭配 `allow_credentials=True` 违反浏览器规范（部分浏览器会拒绝带凭证的通配源），生产环境存在安全/兼容双重隐患。
2. **初始化失败脆弱性**：`init_system()` 中 `SystemInitializer(app, ctx)` 若抛异常，整个应用启动失败且无 try/except 兜底日志。

### 🟡 中危
3. **依赖体积过大**：引入 torch / transformers / paddleocr / playwright 等重型依赖，启动慢、部署包巨大；建议按需拆分 optional-dependencies 加载。
4. **宽松异常吞掉**：心跳与 watcher 均用 `except Exception: logger.warning`，问题可能被掩盖而静默失效。
5. **文件 watcher 依赖**：`core/watcher_setup` 若实现不佳可能造成文件句柄泄漏或 CPU 空转。

### 🟢 低危 / 改进建议
6. **日志重复**：同时使用标准 `logging` 与 `loguru`（依赖中有），存在双日志体系风险。
7. **热重载目录硬编码**：`reload_dirs = ["api", "core", "tools"]` 写死，新增模块需手动维护。
8. **魔法字符串**：版本号 `3.4.0` 在 `pyproject.toml` 与 `main.py` 中重复，建议单一来源。
