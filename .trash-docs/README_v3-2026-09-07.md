## 🧩 为什么不一样

### 1. 工具即一切 —— 没有任何"特殊层"
子代理不是独立架构层，而是 ToolRegistry 里 `task` 工具 handler 的产物。`LLM 决定调 task → 启动新 WorkAgent → 跑同一套 ReActCore`，只是 `personality_prompt` 不同 + `_is_subagent=True`。

```
ToolRegistry (全局单例)
├── SERVER_BUILTIN    12 个内置  (read/write/edit/exec/search/git/todo/...)
├── SERVER_MCP        25+ MCP    (自动发现 · 并行连接 · 同名自动加 {server}_ 前缀)
└── SubAgent          task/orchestrate 本身也是工具
```

**结果**：四类入口共用同一套引擎 —— 行为可预测，没有"主 Agent / 子 Agent"两套栈分裂。

### 2. Plan 步骤契约（postconditions）—— 防止"宣布完成但文件不存在"
传统 Agent 痛点：LLM 说"已完成"，但实际磁盘没文件。引入 `PlanStep.postconditions`：

```python
"file_exists:/path/to/file.md"          # 标记 done 前必须存在
"tool_called:write_file"                # 必须成功调用过
"capability:file_written(path=…)"       # 复合验证
```

`update_step_status()` 在每次标记 `done` 前自动 `_verify_step_completion()`，未满足则注入 `forced_instructions` 让 LLM 下一轮补救。把"口头宣布"绑定到真实状态，是 Agent 工程化的重要进展。

### 3. 12 层中间件管线 —— 洋葱式横切关注点
| Hook 点 | 中间件 |
|---------|--------|
| `on_start` | Todo · 防过早退出 |
| `on_llm_invoke` | Memory → LoopDetection → Clarification → Reasoning → ReActDepth → KEPA |
| `on_plan_check` | ReActCore · 计划推进 |
| `on_wrap_tool_call` | Permission（洋葱最外层）→ ToolCache → validate → handler → bound_result |
| `on_tool_end` | Hook → Compaction → Truncation → Reflection → KEPA → ReActDepth |

洋葱式 Permission：`Permission → ToolCache 命中 → validate_arguments → handler → bound_result 统一截断`。

### 4. L0–L4 八层上下文压缩
| 层 | 机制 |
|----|------|
| L0 | ToolResultBudget — >100K chars 落盘 + 引用 |
| L1a | API Context Mgmt — 清旧 thinking 块 |
| L1b | UI 折叠追踪 |
| L1c | Time-based — gap>60min 只保 5 条 |
| L2 | 缓存断点 metadata |
| L2b | SnipCompact — 前半+后四分之一 |
| L3 | **LLM 9-section 摘要** (Goal/Search/Code/Data/Decisions/Next/Issues/Summary/Config) |
| L4 | 重建消息 + 附件注入 |

V2 还叠了 `ContextBudgetManager` 做 entry-level LLM 摘要，断路器连续 3 次失败自动跳过压缩。

## 🔄 ReAct 循环核心

### 一回合 5 步
```
1. LLM Invoke
   ├─ 正常: 有 tool_calls → 进入 parse
   └─ 空跑: 无 tool_calls
      ├─ 计划完成 → final_answer, exit
      ├─ 空转 ≥6 轮 → final_answer + interrupted
      └─ <6 轮 → inject forced_instructions + retry (≤2 次)

2. on_plan_check
   └─ ReActCoreMiddleware 检查计划步骤是否应自动推进

3. Tools Execute (on_wrap_tool_call, 洋葱式)
   ├─ PermissionMiddleware: 三级权限 + Shell 安全检查
   ├─ ToolCache: 命中直接返回
   ├─ validate_arguments: 参数合法性
   └─ handler → bound_result 统一截断

4. on_tool_end
   ├─ update_step_status: 计划自动推进（postconditions 验证后 done）
   ├─ 步骤失败 → mark failed + retry counter
   └─ HookMiddleware: KEPA 重试决策 → jump_to="retry"

5. 回到 1，直到满足退出条件
```

### 保护机制
| 机制 | 触发条件 | 行为 |
|------|---------|------|
| 空转退出 | `consecutive_idle_rounds ≥ 6` | `interrupted + final_answer` |
| 回合内重试 | 空跑 <6 轮 | inject forced_instructions, rebuild messages |
| LLM 超时 | 60s 无响应 | `interrupted` |
| 重试上限 | 同 LLM 回复最多 2 次空跑 | 用最后一次回复兜底 |
| 完成契约 | postconditions 未满足 | inject forced_instructions + 下轮补救 |
| 最终轮次 | `react_depth > max_iterations` | 标记最终轮 |

## 🧱 中间件管线 12 层

所有中间件按注册顺序依次执行。每个 `HookResult` 可控制流程：`jump_to = "continue" | "end" | "retry"`。

```
build_default_chain():

 ① ReActCoreMiddleware        on_plan_check     核心循环调度
 ② TodoMiddleware             on_start          防过早退出
 ③ MemoryMiddleware           on_llm_invoke     记忆注入 → knowledge_context
 ④ CompactionMiddleware       on_tool_end       LLM 摘要压缩 tool_results
 ⑤ TruncationMiddleware       on_tool_end       兜底截断 (保留最近 5 轮)
 ⑥ LoopDetectionMiddleware    on_llm_invoke     哈希+频率循环检测
 ⑦ ClarificationMiddleware    on_llm_invoke     拦截 LLM 反问 → 等待用户
 ⑧ ReasoningMiddleware        on_llm_invoke     推理优化
 ⑨ PermissionMiddleware       on_wrap_tool_call 三级权限 + Shell 安全 (洋葱最外层)
 ⑩ HookMiddleware             on_tool_end       KEPA 重试决策 → jump_to="retry"
 ⑪ ReActDepthMiddleware       on_llm_invoke+    深度控制 (max 30) + 失败计数
                               on_tool_end
 ⑫ KEPAMiddleware             on_llm_invoke+    知识沉淀 + SharedBus
                               on_tool_end
```

## 🗂 工具系统

### ToolRegistry 注册模型

```
ToolRegistry (全局单例)
├── SERVER_BUILTIN ("__builtin__") — 12 个内置
│   ├─ read_file / write_file / edit_file         文件
│   ├─ execute_python / execute_shell             沙箱执行
│   ├─ web_search / fetch_url                     网络
│   ├─ search_files / git / write_todos           辅助
│   ├─ task — 子代理 (单 Agent)                    ← 不是独立层！
│   └─ orchestrate — 子代理 (DAG 编排)             ← 不是独立层！
│
└── SERVER_MCP (动态发现)
    ├─ CodeGraph (explore/files/callers/callees/impact)
    ├─ Playwright (浏览器自动化)
    ├─ DeepWiki / Context7 (代码知识)
    ├─ MemSearch / EverMem (跨会话记忆)
    └─ ... 25+ MCP 工具
```

### MCP 自动发现
```
get_all_tools() 触发 MCP 连接 (一次性):

  1. _discover_mcp_configs()
     ├─ mcp_client.list_servers()       已注册的 MCP 服务器
     ├─ mcp/*_mcp_server.py             本地脚本自动发现
     └─ .mcp.json                       项目级 MCP 配置

  2. _connect_mcp_servers_parallel()
     ├─ asyncio.gather(每个 server 的 _list_mcp_tools)
     ├─ 单 server 超时 5s, 总超时 12s
     ├─ 去重: 同名工具自动加 {server}_ 前缀
     └─ handler 闭包: 代理到 mcp_client.call_tool(srv, tname, args)
```

### 工具执行流程
```
PermissionMiddleware.check(tool_name, arguments)
  ├─ allowed + need_ask  → 确认消息，等待用户允许/拒绝
  ├─ allowed + !need_ask → 放行
  └─ !allowed             → 硬拒绝

execute_shell → ShellGuard.scan(command)
  ├─ High risk (rm -rf /, dd, mkfs)        → 硬拒绝 + 风险描述
  └─ Medium risk (sudo, chmod, curl|bash)  → 警告 + 继续

ToolCache.get(name, args) → 命中? 返回缓存

validate_arguments(name, args) → 参数合法性
  └─ 失败 → forced_instructions + _validation_error → LLM 下轮修正

handler(args) → result → bound_result 统一截断

ToolCache.set(name, args, response)
```

## 🤝 多 Agent 协作

### 三种路径

```
单 Agent 内部 → task/orchestrate 工具
  └─ 主 Agent 在 ReAct 循环中调用 task/orchestrate
  └─ 启动 WorkAgent 跑同一套 ReActCore，只是角色 prompt 不同

CLI 快捷指令 → /smart /orchestrate /agents
  └─ 自动拆维（搜索/分析/生成/采集/代码/翻译）最多 5 个
  └─ asyncio.gather 并行执行 → 结果汇总
  └─ 降级: orchestrator 不可用时回退 handle_task_with_steps

JS Workflow → bridge.mjs
  └─ Node.js 通过 IPC 调用 Python Agent
  └─ 7 种编排原语 (agent / parallel / pipeline / $dag / workflow / batch / phase)
```

### 跨 Agent 共享资源
| 资源 | 共享方式 | 用途 |
|------|---------|------|
| ToolRegistry | 全局单例 | 所有 Agent 共享同一组工具 |
| SharedBus | 全局单例 (KEPA) | 跨 Agent 知识沉淀和检索 |
| LLMRouter | 全局单例 | 多模型路由 (OpenAI/Anthropic/DeepSeek/OpenRouter/智谱) |
| AgentPool | 8 预热 WorkAgent | acquire/release 模式 |
| Session 存储 | SQLite | 对话日志 + artifact 持久化 |

### 跨 Agent 通信
**KEPA SharedBus（知识闭环）**
```
KEPAMiddleware 每轮 on_tool_end 从工具结果提取知识
  → 存入 SharedBus (按 tag: search/code/analysis/file/kepa)
  → 下轮 on_llm_invoke 查询 SharedBus 获取相关知识
  → 注入到 knowledge_context 供 LLM 参考

特点: 主/子 Agent 共享同一个 SharedBus
      知识带 source 标签 + summary，避免重复注入
```

**Parent Context 注入**：子代理启动时父 Agent 注入 task_description / personality_prompt / work_rules / parent_context，影响某些中间件行为（如 MemoryMiddleware 跳过记忆写入）。

## 🎼 JS 编排引擎

Node.js ↔ Python IPC 桥接，JS 脚本通过 `bridge.mjs` 调用 Python Agent。

### IPC 协议
```
JS → Python: stdout 写入  __IPC__:{"id":1,"type":"agent","data":{...}}\n
Python → JS: stdin 写入   __IPC__:{"id":1,"result":{...}}\n
并行控制:   _ipc_semaphore = 16 (限制同时 agent 调用数)
```

### 7 种编排原语
```javascript
// ① agent — 单 Agent 调用
let r = await agent("分析项目", {
  schema: { type: "object", properties: { summary: {} } },
  model:  "claude-sonnet",
  label:  "代码分析",
  fullResult: true,
})

// ② parallel — 屏障并行 (Promise.allSettled)
let [a, b, c] = await parallel([
  () => agent("任务A"),
  () => agent("任务B"),
  () => agent("任务C"),
])

// ③ batchAgents — 批量并行 (一次 IPC)
let results = await batchAgents([
  { prompt: "扫描", label: "扫描" },
  { prompt: "分析", label: "分析" },
], 120)

// ④ pipeline — 无屏障流水线
let results = await pipeline(
  ["f1.py", "f2.py", "f3.py"],
  (f) => agent(`分析: ${f}`),
  (analysis) => agent(`总结: ${analysis}`)
)

// ⑤ $dag — 声明式 DAG 编排 (拓扑排序 + 并行无依赖 + 上游失败 skip)
let results = await $dag({
  scan:    () => agent("扫描"),
  analyze: { depends: "scan",    task: (ctx) => agent(`分析: ${ctx.scan}`) },
  report:  { depends: ["scan","analyze"], task: (ctx) => agent("报告") },
})

// ⑥ workflow — 嵌套子 Workflow
let r = await workflow("分析项目", { path: "./src" })

// ⑦ phase / log / budget — 辅助原语
await phase("代码扫描")
await log("发现 3 个问题")
console.log(budget.spent())
await budget.report(500, "claude-sonnet")
```

> ⚠️ **不稳定声明**：JS Workflow + V2 Agent 桥接层在复杂并行场景下可能出现超时或状态不同步，建议仅用于探索性编排。

## ⚠️ 已知风险与生产建议

| 优先级 | 项 | 建议 |
|--------|-----|------|
| 🔴 P0 | CORS `allow_origins=["*"]` + credentials | 生产环境必须收敛 |
| 🔴 P0 | `init_system()` 无 try/except 兜底 | 启动失败应有健康检查返回 |
| 🟡 P1 | 4 个 MCP 服务器桌面侧断连 (arbor/codegraph/evermem_search/memsearch) | 排查 Electron sidecar `$PATH` |
| 🟡 P1 | PyObjC 写在通用依赖，Linux 部署会失败 | 移入 `[project.optional-dependencies]` `macos` |
| 🟡 P1 | torch 全量引入，Dock镜像巨大 | CPU-only wheel 或按需加载 |
| 🟢 P2 | 顶层冗余文件 (`nul` / `error_log.txt` / `report_null.html`) | 清理 |
| 🟢 P2 | V1/V2 双架构并存 | 制定迁移路线 + 兼容层到期日 |
| 🟢 P2 | 缺 OpenTelemetry / Prometheus | 已有中间件管线，加 span 即可 |
| 🟢 P2 | 缺 bandit / pip-audit / CHANGELOG | 加入 CI |
